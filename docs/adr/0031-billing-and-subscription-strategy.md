# ADR 0031: Billing and subscription strategy

## Status

Accepted for Phase 29. Written before any payment-processing code, per the
master prompt's explicit instruction: "Before adding billing, write an ADR."
This ADR covers the required considerations and records what is and is not
being built in this phase.

## Context

CrowdSmarter has no plan, subscription, or billing concept anywhere in the
codebase (confirmed by audit: zero `Plan`/`Subscription`/`Billing` models or
fields). The product needs a packaging model, a way to record which plan an
organisation is on, and eventually real payment collection. This development
environment has no live payment-provider account (Stripe, Paddle, or
otherwise) and no way to safely test real charge/webhook flows end-to-end.
Building simulated payment code that has never talked to a real provider
would be worse than not building it: it would look tested when it is not,
and the master prompt explicitly warns against exactly this pattern
elsewhere ("do not market functionality before it meets measurable quality
criteria").

This ADR therefore separates two things that are easy to conflate:

1. **Plan entitlements** — recording which packaging tier an organisation is
   on and enforcing simple, self-contained usage limits. This needs no
   external service and is fully buildable and testable today.
2. **Real billing** — collecting money, invoicing, tax, and payment-provider
   webhooks. This needs a live provider integration and is explicitly
   deferred.

## Decision

### What is being built now (Phase 29)

A new `apps/billing` app owns two models:

- `Plan` — a named packaging tier (`key`, `name`, `trial_days`,
  `max_active_decisions`, `max_active_members`, capability flags for
  advanced foresight and AI assistance, a `support_level` choice, and
  `is_active` to retire a tier from new sign-ups without deleting history).
  Limits are nullable; `null` means unlimited. Three tiers are seeded —
  `team`, `professional`, `enterprise` — as a *proposed* packaging model,
  not a committed pricing page. Changing seeded limits later is a data
  change, not a schema migration.
- `OrganisationSubscription` — one per organisation, recording `plan`,
  `status` (`trialing` / `active` / `expired`), `trial_ends_at`, and an
  optional `billing_contact` (a member designated to receive
  billing-related communication — itself useful before any payment
  provider exists). Every organisation is auto-enrolled in the default plan
  on creation, trialing for that plan's `trial_days`.

Enforcement is real and load-bearing, not decorative: `create_decision()`
and invitation acceptance both call a service-layer guard
(`assert_can_create_decision`, `assert_can_add_member`) that raises a plain
validation error when a plan's limit would be exceeded. The seeded default
plan's limits are generous enough that no existing organisation or test
fixture is affected; enforcement is proven by a dedicated test that
constructs a deliberately low-limit plan.

Nothing here processes a payment, stores a card, or talks to a payment
provider. `OrganisationSubscription.status` moving from `trialing` to
`active` is, for now, a self-service or admin-assisted record change (an
owner picks a plan), exactly like a manually-invoiced customer today.

### What is deliberately deferred, and the plan for each required
consideration when a real integration is built

- **Provider.** Recommend Stripe Billing for the first real integration:
  it owns subscriptions, invoices, tax (via Stripe Tax), dunning, and
  webhooks as a single product, which minimizes custom state machines.
  Should be revisited against final pricing/packaging decisions, not
  assumed here.
- **Subscriptions.** `OrganisationSubscription` is designed to gain a
  `provider_subscription_id` (nullable) when real billing is added, so the
  existing plan/entitlement model does not need to change shape — only
  gain a foreign reference to the provider's own subscription object.
- **Trials.** Already modelled (`trial_ends_at`). A real integration should
  keep trial timing in CrowdSmarter (source of truth for entitlement
  enforcement) and mirror it to the provider's trial fields for invoicing
  timing, not the other way around — the application must never depend on
  a live provider call to know whether to enforce a limit.
- **Invoices.** Out of scope for this phase; when built, invoices should be
  read-only projections of provider data (via webhook), never generated by
  the application, to avoid a second source of truth for what a customer
  owes.
- **Tax/VAT.** Defer to the provider's tax product (e.g., Stripe Tax) rather
  than building jurisdiction logic in this codebase; CrowdSmarter should
  only store the billing contact's country/region as an input to that.
- **Usage.** No usage-metered dimension exists yet (all seeded plans use
  flat per-organisation limits). If a usage-billed dimension is added later
  (e.g., AI review volume), it should be tracked the same way
  `ai_review_quality_metrics()` already aggregates existing records (Phase
  27), not a new metering subsystem.
- **Plan entitlements.** Built now, as above.
- **Grace periods / failed payments.** Model as an `OrganisationSubscription
  .status` value (e.g. `past_due`) once real billing exists, with a
  time-boxed grace window before any enforcement tightens — never an
  immediate hard lockout on a single failed charge.
- **Refunds.** A provider-side operation; the application should only ever
  reflect the resulting subscription status, never compute a refund amount
  itself.
- **Webhooks.** Must be idempotent (see below), signature-verified using the
  provider's signing secret, and processed through the same
  `record_event`-audited service-layer pattern every other mutation in this
  codebase already uses — a webhook handler is a thin view that calls a
  service function, exactly like every other endpoint here.
- **Idempotency.** Every webhook event carries a provider event ID; store
  processed event IDs (a small append-only table, same shape as
  `AuditEvent`) and skip already-processed events before they can double-
  apply a plan change or reactivation.
- **Audit.** Every subscription mutation — plan change, billing-contact
  change, status change — already goes through `record_event`, and any
  future webhook-driven change must do the same, with the provider event ID
  in the metadata for traceability back to the source system.
- **Tenant suspension behavior.** Deliberately *not* wired to any automatic
  lockout in this phase — an expired trial is visible (`is_trial_expired`)
  but not enforced, matching the AI/MFA precedent of never taking an
  automatic punitive action without a human decision behind it. When real
  non-payment suspension is built, it should degrade access (read-only)
  before ever blocking data export or deletion-request rights, so a
  suspended customer can never be prevented from retrieving or removing
  their own data.

## Consequences

- Organisations have a real, enforced packaging concept today without any
  payment-provider dependency or untestable code path.
- The data model is shaped so that adding a real provider later is additive
  (new fields/tables referencing provider objects), not a redesign.
- No invoice, tax, refund, or webhook code exists yet, and none should be
  written until a specific provider is selected and can be integrated
  against a real (even if sandboxed) account — writing it blind would
  produce untested, unverifiable code, which this project has consistently
  avoided (see Phase 26/27/28 for the same reasoning applied to
  integrations, AI providers, and SSO).
- Packaging tiers and limits recorded here are a proposed starting point,
  explicitly not a committed public price list.
