# Localization: scope and status

## What exists today

- **Frontend**: a minimal, dependency-free i18n foundation (`frontend/src/lib/i18n.ts`) —
  a typed per-page message catalog (`defineCatalog`), a locale store built with
  `localStorage` and `useSyncExternalStore` (`useLocale`/`setLocale`), and a retained
  `<LanguageSwitcher>` component. English is the only locale exposed in the current
  product. `LANGUAGE_SELECTION_ENABLED` is deliberately `false`, public pages do not
  render the selector, and stale stored preferences are ignored. French and Arabic
  catalogs remain in the repository as incomplete groundwork rather than a product
  promise. The Arabic infrastructure includes right-to-left document handling; email
  addresses, passwords, and one-time codes remain left-to-right.
- **Backend**: Django's standard i18n machinery is active (`LocaleMiddleware`,
  `LANGUAGES`, `LOCALE_PATHS`), with `.po`/`.mo` translation files under
  `backend/locale/{fr,ar}/LC_MESSAGES/`.

## Coverage — incomplete and not currently exposed

The retained catalogs prove the locale plumbing but do not constitute a translated
product:

- **Catalogued in part**: the public landing page, Open Session public join flow,
  account-creation flow, and core sign-in screen. Backend invitation email strings also
  exist for French and Arabic.
- **Still English-only**: much of the public experience and the authenticated application
  (organisation workspace,
  decision reasoning, evaluations, disbursements, everything behind `/app`), most form
  validation messages, and most other transactional emails.

Do not re-enable `LANGUAGE_SELECTION_ENABLED` or restore the public selector until the
chosen language has complete journey coverage, native-speaker review, and product
approval. Extending the underlying coverage still means adding a `defineCatalog` in
`frontend/src/lib/catalogs/` and calling `useTranslations(catalog)` in the component.

## Translation quality: AI-assisted, unreviewed

Every French and Arabic string in this codebase — both the frontend catalogs and
the backend `.po` files — was produced with AI assistance and has **not** been reviewed
by a native or fluent speaker. This is stated explicitly, not hidden: treat the current
copy as a structurally-complete placeholder that unblocks the i18n plumbing, not as
final, publish-ready translation. Before enabling French or Arabic copy for a
real funder, community, or applicant, have a native speaker review:

- `frontend/src/lib/catalogs/*.ts`
- `backend/locale/fr/LC_MESSAGES/django.po`
- `backend/locale/ar/LC_MESSAGES/django.po`

## Regenerating backend translations

```bash
docker compose exec backend python manage.py makemessages -l fr -l ar --no-obsolete
# edit backend/locale/{fr,ar}/LC_MESSAGES/django.po
docker compose exec backend python manage.py compilemessages
```

`makemessages`/`compilemessages` require the GNU gettext tools (`msguniq`, `msgfmt`).
They are not part of the base backend image; install them in the running container with
`apt-get install gettext` before regenerating, or add the package to the Dockerfile if
translation work becomes routine.
